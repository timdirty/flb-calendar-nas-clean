# **圖片/影片上傳系統建置與整合方案**

# **系統總體架構**

圖：系統總體架構示意圖（參考 Google Photos 架構）

整體架構方面，前端介面由 Web UI 與 LINE LIFF（基於瀏覽器的 LINE 應用）構成，用戶端經由 Nginx HTTPS 反向代理與後端服務通訊。後端可採用微服務化設計，包括負責接收上傳與 CRUD 的 API 伺服器、媒體處理（縮圖生成、影片轉碼）的工作者服務，以及負責搜尋/分群等功能的其他服務。儲存層則可使用 Synology NAS 內部掛載卷或部署 S3 相容的 MinIO 作物件儲存 。借鑒 Google Photos 的經驗，其所有媒體元資料都儲存在 Cloud Spanner，後端由數十個微服務與 Flume 管線協同作業 ；類似地，我們的系統可將媒體檔（原始檔）儲存在物件儲存層，並將索引/記錄存在資料庫中，搭配多個微服務分工處理上傳、搜尋、轉碼等任務。

# **上傳流程與後端處理**

- 用戶上傳：使用者在 Web UI 或 LINE LIFF 中挑選檔案上傳（支援批次或斷點續傳），檔案透過 HTTPS 經 Nginx 代理轉送至後端 API。
- 資料儲存：後端收到檔案後立即將原始檔存入持久層（如掛載的 NAS 文件系統或 MinIO 儲存桶），並在資料庫建立相對應的索引/記錄。根據 Dropbox 經驗，縮圖應另存為獨立檔案，而非覆蓋原圖 。
- 後端處理：儲存完原始檔後，將處理任務送入佇列（如 RabbitMQ、Redis 等），由工作者服務異步執行後續步驟。工作者使用 FFmpeg 擷取影片封面並轉碼為通用格式（例如 H.264 編碼的 MP4 ），並運用影像處理函式庫或服務（如 ImageMagick、ImageProxy）產生多尺寸縮圖。縮圖檔與轉檔後的影片檔同樣存入物件儲存，並更新資料庫狀態。
- 即時預覽：上傳後可立即透過前端顯示縮圖，後端亦可提供預覽請求，例如直接回傳已儲存的縮圖或使用即時影像服務（如 imgproxy）動態調整大小。

# **快取機制**

- 影像快取：可使用專用的影像代理服務，如 imageproxy，該服務可在記憶體或磁碟進行快取 。前端載入相簿時，直接加載已有縮圖，減少即時計算開銷。此外，可利用 Nginx 的快取設定（如 proxy_cache）與適當的 Cache-Control 標頭，加速靜態檔案的傳送。若服務對象地理位置分散，可配合 CDN 進行全球快取，但對內部部署應權衡外部流量成本。
- 資料緩存：針對常用的相簿列表或搜尋結果，可在服務層（如 Redis）暫存列表或縮圖路徑，降低資料庫查詢次數。對於縮圖/影片等靜態資源，可在檔案系統層級設置 cache（如 Btrfs/LVM 快取或 Synology NVMe SSD 快取）以提高 I/O 效能。

# **縮圖與影片轉碼策略**

- 影片轉碼：使用 FFmpeg 將上傳的影片轉為網路友善格式（例如 H.264/AAC 編碼的 MP4 ），並從影片中擷取縮圖（可指定時間點作為封面）。若需要多種解析度，可生成多個檔案或採用 DASH/HLS 等串流格式以提供不同品質。
- 縮圖生成：可在上傳後同步產生常用尺寸（如相簿檢視與查看器使用的中小尺寸），縮圖檔儲存在物件儲存中。對於更彈性的需求，可使用即時影像處理服務（如 imgproxy），它能根據 URL 參數動態縮放圖片，減少需預先生成的版本 。Imgproxy 支援 WebP、AVIF 等高效格式 ，並具備安全防護措施（檢查異常大小、URL 簽名 ），保障服務穩定。使用這些工具能加速相簿開啟時縮圖載入，同時降低儲存成本。

# **適合的開源/商用套件**

- PhotoPrism：AI 驅動的開源相片管理平台，可支援 RAW、HEIC/HEIF、Live Photos、MP4、MOV 等多種格式 ，並內建縮圖與索引功能 。適合部署於 NAS 上，並提供 Web UI 及 API。
- MinIO：自架設的 S3 相容物件儲存服務，可將 Synology NAS 作為儲存後端 ，方便與其他服務整合並橫向擴充。
- 影像代理（ImageProxy/Imgproxy）：專用的影像處理服務，可對外部請求的圖片進行即時縮放、裁切等操作，並在記憶體或磁碟快取結果 。其中 Imgproxy 更強調效能與安全（支援 URL 簽名、防範影像炸彈 ）。
- FFmpeg：開源影片編碼與處理套件，用於轉檔、萃取影片縮圖，支持廣泛格式 。可容器化執行以處理上傳影片。
- MongoDB/GridFS：可作為檔案儲存方案之一，但如要儲存大量小縮圖，GridFS 的區塊系統會引入額外開銷；對於縮圖等小檔案，建議直接存入檔案系統或物件儲存，更為高效 。
- Nextcloud：自架雲端存儲平台，內建文件與相簿管理，可用作一般檔案分享；但其縮圖與媒體處理功能不如專用系統，適合檔案同步需求較高的場景。

# **Docker 容器與 NAS 儲存整合**

- 容器部署：可使用 Synology DSM 內建的 Docker/Container Manager，或自行編寫 Docker Compose 檔，將相簿應用、物件儲存（MinIO）、資料庫等容器拉起。利用 Docker 卷（Volume）將 NAS 共享資料夾掛載到容器內部。例如為 MinIO 容器建立 /data 掛載點對應 NAS 上資料夾 ；其他服務（如資料庫、PhotoPrism 的媒體目錄）也同樣透過卷指定到 NAS 路徑，確保資料持久化。
- 反向代理整合：利用現有 Nginx + HTTPS 設定，為各容器服務配置子域名或路徑轉發（proxy_pass）。可透過虛擬主機機制將不同域名（如 photos.example.com、api.example.com）指向相應容器埠口，使外部訪問經由 Nginx 安全代理到內部服務。此方式可統一 SSL/TLS 認證並簡化服務部署。

# **效能優化與併發建議**

- 資源配置與併發：Synology DS923+ 標配 4GB RAM、雙核心 CPU ，可擴充至 32GB 以提升效能。考量影片轉碼為 CPU 密集型任務，應限制同時運行的 FFmpeg 實例數量或依需求水平擴展，避免 CPU 飽和導致延遲過高。同時可使用 M.2 NVMe SSD 快取功能 提升磁碟 I/O 效率，加速大量縮圖與檔案存取。前端載入可採用分頁或懶加載技巧減少一次性請求數量；後端則應優化 I/O 和運算流程，必要時使用記憶體快取（如 Redis）加速熱點數據存取，以緩解高併發負荷。系統架構應採用非同步機制（佇列、事件驅動）分離請求與耗時處理，以提供良好的使用者體驗並提高服務可擴充性。
- 壓力測試：針對約 50 人同時上傳/瀏覽的需求，可透過負載測試工具評估系統瓶頸，如網路頻寬、CPU 或 I/O 並發數。若未來需求增加，僅靠單台 NAS 可能有限，可考慮對圖片服務進行水平擴充（多台 NAS 或混用雲端儲存）或結合 CDN 分散流量。

# **安全性設計建議**

- 傳輸與存取安全：系統需全程使用 HTTPS（已由 Nginx 配置），防止中間人攻擊。前端與後端間的認證機制可採用 LINFF Token（若需辨識用戶），但可因應「開放瀏覽」需求，只限制重要操作。檔案上傳時應檢查檔案類型與大小，避免惡意檔案（如執行檔或腳本）被上傳。存放區域若透過網頁可直接訪問，務必關閉目錄列表功能，只允許透過 API 或已知檔名存取檔案。
- 容器與設定安全：不要在 Docker 容器內硬編碼密碼，應使用環境變數或 Docker Secret 機制。對 MinIO 等容器設定強密碼（可使用長隨機字串作為 MINIO_ROOT_PASSWORD）。定期更新 Docker 映像與 Synology DSM 以修補已知漏洞；對使用者上傳的檔案可考慮部署掃毒或檔案篩檢機制。
- 影像處理防護：若採用 imgproxy 等即時影像服務，應啟用其內建防禦機制，如影像炸彈檢測與 URL 簽名 ，以避免外部惡意用戶透過大量隨機參數發起拒絕服務攻擊。
- 日誌與備份：部署日誌系統與監控（如統計上傳/下載量、失敗請求等），及時發現異常行為。定期備份 NAS 上之重要資料（可利用 Synology Hyper Backup 等工具），並設置 RAID 冗餘與快照功能，以防硬體故障或資料損毀。

參考來源: 本方案結合了 Google Photos、Dropbox 等企業級服務的媒體處理經驗 ，並運用 PhotoPrism、MinIO、FFmpeg、imgproxy 等開源組件 於 Synology 環境中構建高效、彈性的圖片/影片上傳平台。
